# Infra — Render Deploy Configuration

## Topology

**One Render Web Service.** A single Node.js process runs the Express server
from `server/`, which serves three things over the **same origin**:

1. **REST API** — all `/api/*` routes (health, workshops, ideas, votes, coach, etc.)
2. **Socket.IO** — the WebSocket endpoint rides on the same HTTP server (no separate WS port)
3. **Built React assets** — static files from `client/dist/` with an SPA fallback for client-side routing

No CORS configuration is needed because the client and server share one origin.
No reverse proxy, no CDN, no separate static-site service — just one process.

### Why single-instance

The backend uses an in-memory `RoomStore` (no database). Multiple instances would
each hold their own divergent state, so `numInstances` **must stay 1**. Scaling out
would require adding a Redis adapter for Socket.IO and a shared store — out of scope.

### Render plan

`starter` — the Free plan spins down idle instances, which kills every open socket.
Starter keeps the process resident so WebSocket connections survive.

## render.yaml — Blueprint

The file `render.yaml` in this directory is a [Render Blueprint](https://render.com/docs/blueprint-spec).
It is applied via the Render Dashboard (Blueprints → New) or the Render API.

| Field | Value | Notes |
|---|---|---|
| `type` | `web` | Web Service |
| `name` | `minutemaid-workshop` | Matches root `package.json` name |
| `runtime` | `node` | Node.js runtime |
| `plan` | `starter` | Avoid Free (spins down, kills sockets) |
| `region` | `oregon` | US West; adjust if latency demands |
| `buildCommand` | `npm install && npm run build` | Installs workspaces, builds client + server |
| `startCommand` | `npm start` | Resolves to `npm run start --workspace server` |
| `healthCheckPath` | `/api/health` | Must return 200 for deploy to be live |
| `numInstances` | `1` | In-memory store requires single instance |

## Environment Variables

| Key | Source | Purpose |
|---|---|---|
| `PORT` | **Auto-injected by Render** | Server binds `0.0.0.0` on `process.env.PORT`. Do not set in blueprint. |
| `NODE_VERSION` | Blueprint (`"20"`) | Pins the Node runtime for `nvm`-style builds |
| `NODE_ENV` | Blueprint (`production`) | Enables production optimizations in Express, Vite, etc. |
| `GEMINI_API_KEY` | **Manual** (`sync: false`) | Google Gemini API key for the LLM coach. Set in Render Dashboard → Environment. |
| `MODERATOR_KEY` | **Auto-generated** (`generateValue: true`) | Bearer token for moderator-authenticated REST/socket calls. Render generates a random value on first deploy. |

### LLM key

The coach system is provider-agnostic and auto-detects which key is present
(`GEMINI_API_KEY`, `OPENAI_API_KEY`, or `ANTHROPIC_API_KEY`). **Exactly one**
must be set. The current blueprint uses `GEMINI_API_KEY` with `sync: false`,
meaning it is never synced from the repo — you must paste it into the Render
Dashboard manually. **Never commit an LLM key to the repo.**

### MODERATOR_KEY

Generated by Render on first deploy. Copy it from the Render Dashboard →
Environment tab after the initial deploy and distribute it to workshop operators.

## Local Production Build Verification

Before pushing to Render, verify the production build works locally:

```bash
# 1. Install all workspace dependencies
npm install

# 2. Type-check both client and server
npm run tsc

# 3. Build everything (client bundle + server)
npm run build

# 4. Start the production server (reads client/dist + serves /api/*)
NODE_ENV=production MODERATOR_KEY=test-key-12345 GEMINI_API_KEY=your-key npm start

# 5. Verify health endpoint
curl http://localhost:3000/api/health
# Expected: {"ok":true,"uptime":...}  with HTTP 200
```

If `npm run build` or `npm start` fails locally, it will fail on Render. Fix
locally before pushing.

## Post-Deploy Verification Checklist

After the first Render deploy reaches `live` status, verify each item:

1. **Health endpoint returns 200**
   ```bash
   curl -s -o /dev/null -w "%{http_code}" https://<your-service>.onrender.com/api/health
   # Expected: 200
   ```

2. **Socket.IO connects and round-trips**
   - Open the participant or big-screen URL in a browser.
   - Confirm the socket connects (`io()` handshake succeeds, no console errors).
   - Submit an idea on the participant view — it should appear on the big screen
     within the same second (socket event `idea_added`).

3. **One REST call succeeds**
   ```bash
   # Create a room (requires moderator key)
   curl -X POST https://<your-service>.onrender.com/api/workshops \
     -H "Authorization: Bearer <MODERATOR_KEY>" \
     -H "Content-Type: application/json" \
     -d '{"code":"TEST"}'
   # Expected: 200/201 with a workshop JSON body
   ```

4. **Reconnect survives redeploy**
   - Open a participant connection in a browser tab.
   - Trigger a redeploy from the Render Dashboard (or push a new commit).
   - The client should detect the disconnection, show a reconnecting state,
     and re-establish the socket connection once the new instance is live.
   - No manual page reload should be required if Forge implemented reconnect logic.
